# Patch content is anchored and bounded, not verified

The verifier's central move is to allowlist a safe grammar and reject everything
outside it. That has no purchase on a patch's `new` field, because there is no
grammar for "safe source code". Of the four existing phases, schema contributes
only a length cap, the markdown allowlist is inapplicable, and provenance has no
analogue — there is no "line falls inside a diff hunk" for content the model
invented. Only the secret scan transfers cleanly.

The prover does not close this either. Frame conditions constrain *which* files
change and ordering constrains *when* writes happen; neither says anything about
what the new code does. A plan can be `unsat` against every policy in §20 and
still patch a file with a line that exfiltrates a credential at import time.

So for remediation, the verifier is containment rather than quality control. It
bounds where the agent can write and what shape the request takes. §2.5 already
warns that "in a system where the verifier is the only quality control, 'safe'
quietly gets read as 'fine to post'"; remediation widens that gap, because a
wrong review comment is noise while a wrong patch is a merge candidate. What
makes this acceptable is ADR-0001: the effect is a branch and a pull request,
which are inert, reversible and human-gated. Nothing executes the patch until a
human merges it. The pull request is the gate.

Two checkable properties are enforced in place of verification:

**Anchoring.** A patch's `old` field must match the file's current bytes exactly
at the reviewed SHA. This is the closest analogue to provenance a patch can
have: it proves the model was looking at the actual file, and it fails closed if
the file changed underneath, the same posture as the head-SHA guard.

**Bounding.** Policy caps the number of patched files and changed lines per
patch, and carries a path denylist for paths that must never be patched
regardless of whether the pull request touched them.

**Frame.** A patch's `path` must be a file the pull request already touched —
§20's frame condition as written, checked against the `changed_files` the
verifier already holds. This follows the precedent the
`provenance_boundary_adjacent_bug` eval scenario already sets for findings:
falsifiability beats coverage, and a real bug goes unreported rather than weaken
anchoring. An unanchored patch is worse than an unanchored comment.

A policy allowlist of extra patchable paths (`tests/**`, say) was considered and
rejected for now. It would give patchable paths two sources, and their
interaction with the denylist makes evaluation order security-relevant — the
shape of the dotfile-path defect in §17, where the pattern was enforced exactly
as written and the written pattern was wrong. Restricting to `changed_files`
keeps the frame condition a ∀-claim over a closed set the verifier already
possesses, with no new trusted input.

## Consequences

- `verify()` currently takes `(artifact, diff_text, changed_files, policy)` and
  reads no files, which is part of why it is easy to test. Anchoring requires
  file content at the reviewed SHA, so the interface and every test fixture
  grow a content source. This is the largest change to the verifier's shape.
- The rendered pull-request body must carry the same "generated by an AI model,
  counts toward no approval" notice the review comment does, plus the policy
  hash. Patch content being unverified by construction has to be visible to a
  reviewer, not just recorded in an ADR.
- The path denylist is policy data, so a consumer can forbid paths specific to
  its repository. It applies on top of the `changed_files` frame, so it is a
  narrowing of an already-closed set rather than the sole bound — which is why a
  denylist is acceptable here despite allowlisting being the rule everywhere
  else in the policy.
- Remediation fixes what the pull request broke, in the files the pull request
  touched. The most valuable remediation — "you changed this function, here is
  the regression test" — is usually a new file under `tests/`, which by
  definition the pull request did not touch, so it is out of scope. This is the
  limitation most likely to want revisiting, and it needs its own ADR when a
  concrete plan requires it.

## Addendum: the closed set has to be closed by the executor

Added 2026-08-01, after review found the frame condition quantifying over an
untrusted set.

The frame is "a ∀-claim over a closed set the verifier already possesses, with
no new trusted input" — the sentence that makes it a containment argument rather
than a filter. What closes the set is where `changed_files` comes from, and in
`execute_plan.py` it came out of the downloaded bundle, i.e. from the job that
also ran the generator. The set was closed by the plan job.

So the ∀-claim held over whatever list that job supplied. A `diff.patch` and
`changed_files.json` naming a file the pull request never touched made a `patch`
or `suggest` step on that file provenant, and anchoring does not catch it:
anchoring proves the model read bytes that are really in the quarantine, and a
contributor-authored file is really there. Reproduced end to end — a suggest
step on `src/forged.py` reached the delivery decision.

The prover made it slightly worse. `verify_plan` takes the parsed list and
`prove-cli` takes a `--changed-files` PATH, so a fix that re-fetched the list for
the verifier while leaving the prover pointed at the bundle's file would have the
two gates proving different things about different files — with the frame proof,
the one this ADR is about, reading the untrusted copy.

**Both executors now establish their own provenance inputs.** `post.py` and
`execute_plan.py` call `prepare_context.fetch_anchored_pair`, and
`execute_plan.py` writes the fetched list to `changed_files.fetched.json` and
points the prover at that — one list, both gates. The bundle's copies remain in
the artifact as reproducibility evidence, which is all they were ever load-bearing
for.

*(Since [ADR-0016](0016-retire-the-typescript-prover-consolidate-on-python.md)
retired the prover, the fetched list goes straight to `verify_plan` and the
written-out file is gone; the property — provenance inputs are the executor's
own fetch, never the bundle's — is unchanged.)*

Nothing about the frame condition itself changes. This is the ADR's own reasoning
being made true: `changed_files` is only a closed set if the process making the
∀-claim is the one that closed it.
